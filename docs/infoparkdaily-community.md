# InfoparkDaily community section

The separate `/infoparkdaily/` section is linked from the main site's **About Us → InfoparkDaily** menu. The existing `/media/` page remains available as **About our community**.

## Public pages

- Home, job search and details, worker directory and profiles, about/how it works, contact.
- Current curated listings come from the existing `data/jobs-data.js`. Applications to those listings go directly to the employer's stated channel. Marking one as applied records a personal reminder; it does not submit an application.
- Approved community jobs and worker profiles come from Firestore. Empty directories invite real registrations; no sample members are seeded in production.
- Public HTML is generated by `npm run build:community`; the browser refreshes listings from the shared data and approved community records. Run this build after updating the curated job data or community source.

## Member workflows

Firebase Authentication reuses the Career Tools project. Email verification is required before writing account records. Google sign-in and email/password accounts share the same workspace.

- Worker profile submission → admin review → public directory.
- Employer job submission → admin review → public job post.
- Worker application or employer invitation → employer hire request → admin approval → private chat.
- Worker may request completion; employer confirms completion. Each participant can then leave one public review.
- Saved jobs, employer applications, job editing/closing, member documents and account settings are separate workspace pages.

### Documents

Three private Firestore document slots (`resume`, `certificate`, `other`) each accept up to 700,000 bytes. A resume can be copied into an application atomically with its submission. That snapshot is readable only by the participants and authorised admins. Removing the private original does not remove an already-shared copy. Binary fields and profile photo fields are excluded from indexes.

No paid storage or billing upgrade was enabled. This small-document limit uses the existing Firebase setup. A future higher upload limit should use private object storage with equivalent ownership and application-sharing checks.

## Administration

`/infoparkdaily/admin/` checks a server-managed `marketAdmins/{verified-email}` registry. Browser clients cannot create or change registry entries. There is no first-user admin fallback. The authorised administrator is **enitexaai@gmail.com**; sign in with that email and complete the initial account details to open Community review.

Administrators can review jobs and worker profiles, approve hire requests, inspect private documents for review, and export the displayed records as CSV. They cannot access private Career Tools resumes through marketplace privileges.

## Local development and checks

Run the existing `npm run dev` and visit `http://localhost:8000/infoparkdaily/`.

- `npm run build:community` builds the bundle and pre-renders the five public pages.
- `npm run check` and `npm test` retain the existing application's checks.
- Firestore and Auth emulators must run as project `demo-infoparkdaily`, on ports 8080 and 9099, before community tests.
- `npm run test:community` checks ownership, review gates, document sharing, applications, chat and reviews against emulator rules.
- `node tests/infoparkdaily/workflow.mjs` checks the worker/employer/admin journey and mobile pages with local Chrome. It clears only the **demo** Firestore project.
- `node tests/infoparkdaily/auth-flow.mjs` checks signup, verification and password reset. All email actions remain in the Auth emulator.

The browser tests set `sessionStorage.ipd_market_emulator` to `1` only on localhost. Normal browsing uses the real Firebase project. Test records and test messages are never inserted into production.

## Publishing

Preserve the existing GitHub Pages deployment. Build the community section, validate, and publish the checked commit. Deploy marketplace security rules and indexes with the existing Firebase configuration when they change. The main service worker bypasses community routes and Firebase requests; authenticated records are never rendered into static HTML.
